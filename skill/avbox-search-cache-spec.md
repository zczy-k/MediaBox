# 搜索本地缓存方案评估:可行性、存储、失效与一致性

> 项目:MediaBox / AVBox(TVBox OSC fork;仓库根 = 本文件所在目录的上一级)
> 配套:先读 `SKILL.md`(通用规范 + 文档地图)、`avbox-kv-mmkv-spec.md`(存储约束)、`avbox-playback-service-spec.md`。
> 状态:**评估与设计(未实施)**。本文只做判断与方案,不改代码。
> 触发诉求:启动时联网拉取各源影片文字信息并缓存,后续搜索优先本地检索,以减少实时请求、提升搜索速度。

## 0. 摘要(结论先行)

| 问题 | 结论 |
|---|---|
| 启动时**全量**拉取所有源目录并本地索引 | **不可行**。协议层没有"导出全量"的能力;成本层是百万级请求 / 数十 GB 流量 / 数小时;存储层是 GB~TB 级 |
| 是否值得做缓存 | **值得,但要换形态**:缓存「关键词 → 结果」而不是「源的整个目录」 |
| 存储会不会随数据量暴涨 | **全量方案必然暴涨**(线性于 源数 × 片数 × 记录宽度,再加 2~3× 索引膨胀);按需方案有硬上限,不随源数增长 |
| 退出时自动清除 | **不能作为主机制**(Android 不保证进程退出回调),且会把收益清零;应以 TTL + LRU + 阈值为主 |
| 推荐 | **P0 = 按需关键词结果缓存 + 负结果缓存**;P1 = 首页源单源索引(可选);全量索引不做 |

一句话:**用户的痛点是"328 个源里 289 个超时"(`echo-searchplan` 真机实测),不是"搜索算法慢"。对症的是砍死源 + 缓存结果,不是把目录搬本地。**

## 1. 现状实测基线(真机 v1.0.7-diag)

所有数字均为本机真机实测或从本仓库代码/数据直接推导,不是行业经验值。

| 项 | 实测值 | 来源 |
|---|---|---|
| 参与搜索的源数 | **328** | `echo-searchplan token=2 total=328 fast=328` |
| 单轮全站搜索耗时 | **≈ 146 秒**(2.4 分钟) | `11:55:24.882` → `11:57:51.510` |
| 单轮终态分布 | timeout **289** / empty 35 / hit **4** | `echo-searchplan batch-summary`(9 个 batch 累加) |
| 单源搜索超时 | 8 000 ms | `SearchViewModel.SEARCH_TIMEOUT_MS` |
| 并发上限(信号量) | 32(默认,可调 16/32/48/64) | `HawkConfig.SEARCH_THREADS` |
| 批大小 | 首轮 24 / 后续 50 | `SearchBatchPolicy.FAST_ROUND_SOURCE_LIMIT / DEFAULT_BATCH_SIZE` |
| 搜索是否已有结果缓存 | **没有**。只有热搜词当日缓存 | `SearchViewModel` 仅 `HOME_HOT` + `HOME_HOT_DAY` |
| 应用数据总占用 | **59 MB** | `du -sh .`(`run-as com.zczy.mediabox.diag`) |
| 其中数据库 | `tvbox.v4.db` **77 KB** | 同上 |
| 其中 KV | `files/mmkv/avbox_kv` 64 KB | 同上 |

**这张表已经说明了主因**:一轮搜索 328 个源里 289 个超时(88%),真正可用的源不到 15%。耗时几乎全花在"等死源超时"上。

### 1.1 现有搜索链路(为什么"本地检索"不是小改动)

```
用户输入关键词
   ↓
SearchViewModel.runSourceSearch   ← 逐源并发调度,8s 超时,信号量 32
   ↓
SearchLoader.getSearch(sourceKey, wd)
   ↓  把关键词**原样透传**给源站:
   type 0/1  GET {api}?ac=detail&wd=<关键词>      ← XML / JSON 站点
   type 3    Spider.searchContent(wd, false)      ← csp jar,阻塞调用
   type 4    GET {api}?ac=detail&wd=&quick=false&extend=…   ← 带 extend
   ↓
SourceResultParser → AbsJson/AbsXml → Movie.Video
   ↓
SearchSettings.matches(name, alias, keyword, mode)   ← **本地只做"过滤 + 排序",不做"检索"**
```

关键事实(代码原话,`SearchSettings.queryVariants` 的 KDoc):
> 客户端搜索是**原样把关键词透传给源站搜索接口**,不做本地检索。

也就是说,**今天根本不存在"本地检索"这件事**;关键词怎么匹配由源站决定,客户端只在拿回来的结果里按 `SearchSettings.normalize` 的口径过滤与排序。

## 2. 可行性判断

### 2.1 协议层:源站没有"导出全量目录"的接口

TVBox 源协议(`ConfigParser` + `Spider`)对外只有三类取数能力:

| 能力 | 参数 | 能否枚举全量 |
|---|---|---|
| `homeContent` / `sorts` | 无 | 只给**分类骨架**,不含条目 |
| `categoryContent` | `t=分类id` + `pg=页码` + `f/ext=筛选` | **只能分页枚举**,且**必须逐个分类 × 逐个筛选组合** |
| `searchContent` | `wd=关键词` | **必须有关键词**,无法列全量 |

`categoryContent` 是唯一可枚举入口,但它有三个硬约束:

1. **必须按分类分别拉**:`t` 是分类 id,没有"t=all"。
2. **必须按筛选组合分别拉**:`sortData.filterSelect` 每个组合是一份**独立列表**(如"电影 + 2023 + 动作"),`ListLoader.getListFromApi` 里 `f` 参数就是它。全量 = 分类 × 筛选组合。
3. **深翻页普遍不支持**:多数站点 `pg` 超过某值(常见 50~100)后返回空、或重复第 1 页、或直接 502。**目录深处的内容事实上拿不到**。

结论:**"全量拉取"这个前提在协议层就不成立**。能拿到的只是"每个分类的前若干页",而这恰好会造成最难查的一类事故 —— 用户搜的片在源站有、却在本地索引里没有 ⇒ "明明有却搜不到"(本地假阴性)。

> 这一点与本仓库既有原则直接冲突。`SearchBatchPolicy.splitFastRoundSources` 的注释写得很明确:
> 「静默丢弃慢源会让"库里明明有这部片子却搜不到",那是**准确度事故**,不是优化。」
> 全量索引方案的本质,是把这条准确度事故从"少数慢源"扩大到"所有源的目录深处"。

### 2.2 成本层:请求数、流量、时间(量级估算)

以本机 328 个源、一个中等规模聚合站为例。**注意:以下为量级估算,假设已显式列出;真实值因站而异,但数量级不会变。**

单源枚举请求数:

```
假设 30 个分类 × 每分类 209 页 + 筛选组合(保守按 1.5 倍计)
≈ 30 × 209 × 1.5 ≈ 9,400 请求/源
```

| 项 | 全量(328 源) | 仅 30 个常用源 |
|---|---|---|
| 请求数 | ≈ **308 万** | ≈ 28 万 |
| 流量(每页 30 KB,不含播放地址) | ≈ **92 GB** | ≈ 8.4 GB |
| 流量(每页 300 KB,JSON 源 `ac=detail` 含 `vod_play_url`) | ≈ **924 GB** | ≈ 84 GB |
| 耗时(32 并发、平均 0.5 s/请求) | ≈ **13 小时** | ≈ 73 分钟 |

**每页 300 KB 不是危言**:`AbsJson` 的字段样例里,单条记录的 `vod_play_url` 就有 12 集 × ~60 字符;一部 40 集剧集的播放地址串可达 5~10 KB。JSON 型源的 `ac=detail` 把播放地址一并返回(`AbsJson.AbsJsonVod.toXmlVideo()` 第 148~163 行确实把它映射进 `urlBean`),所以列表页能很轻松到几百 KB。

除了流量和时长,还有三条**非技术性但决定性**的风险:

- **会被源站风控**:328 个站在几小时内各被翻几百页,是教科书式爬虫特征;IP 被封会连带影响**正常播放取流**(同一个出口 IP)。
- **移动网络下不可接受**:92 GB~924 GB,而用户的开机场景经常是移动网络。
- **启动路径被拖垮**:启动时做 13 小时的任务不成立;放后台又会被系统杀,还会持续耗电。

### 2.3 语义层:本地检索复刻不了现状的匹配语义

即便目录拿到了,本地检索也要复刻 `SearchSettings` 的整套语义,而这套语义**不是简单的 `contains`**:

| 语义 | 现状实现 | 复刻难度 |
|---|---|---|
| 归一化 | 全角→半角 → 删括注及内容 → 删空白标点 → lowercase | 可复刻 |
| 别名参与匹配 | `alias`(源站 `vod_sub`/`vod_en` 合并,`\|` 分隔) | 需在索引里存别名 |
| 番号前缀匹配 | `MIAA-195` 命中 `MIAA-195 标题`,但 `MIAA-19` **不得**命中 `MIAA-195` | 需要专门索引策略 |
| 三档模式 | `All / Smart / Exact`(用户可切换,默认 Smart) | 索引只能做**候选召回**,仍须二次过滤 |
| 相关度排序 | 5 级评分(相等/开头/包含/多词全含/别名相等) | 需保留原评分函数 |

也就是说:本地索引**最多只能替代"召回"这一步,不能替代"过滤 + 排序"**。而"召回"恰恰是源站 `searchContent` 做得最好的部分(它用的是站内 `LIKE`,覆盖全库)。

另外,中文子串检索需要 **bigram(二字组)倒排索引**,否则只能 `LIKE '%关键词%'` 全表扫。10M 行 LIKE 扫描是秒级,不可用;而上 bigram 索引,**索引本身体积约为原文本的 2~3 倍** —— 这直接把第 3 节的估算再乘 3。

### 2.4 风险清单

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| R1 | 本地假阴性(有片搜不到) | **高** | 深翻页拿不到 + 部分源枚举失败 ⇒ 用户认为"App 搜不到这部片",比慢更伤 |
| R2 | 启动期流量/时长不可接受 | **高** | 92 GB~924 GB、数小时;移动网络场景直接废掉 |
| R3 | 源站风控封 IP,连带影响播放 | **高** | 同一出口 IP,封了会影响取流与图片加载 |
| R4 | 存储线性暴涨 | **高** | 见第 3 节 |
| R5 | 索引语义复刻不全 | 中 | 别名/番号/模式;只能召回不能判定 |
| R6 | 源目录日更,索引天然过期 | 中 | 新片当天搜不到;见第 5 节 |
| R7 | type 3(csp jar)源不可离线枚举 | 中 | jar 必须运行;失败即整源无索引 |
| R8 | 与既有"源屏蔽"机制互相干扰 | 低-中 | 索引会覆盖到已被屏蔽的死源,**浪费的正是最贵的那部分成本** |
| R9 | 合规面 | 中 | 批量抓取第三方站点目录,比按需请求更接近"爬站" |

### 2.5 结论:拆开看,哪部分可行

| 子诉求 | 可行性 | 判断 |
|---|---|---|
| 启动时**全量**拉取所有源目录并建立本地索引 | ❌ | 协议不支持 + 成本不可接受 + 会引入假阴性 |
| 启动时拉取**少数几个**常用源的目录 | ⚠️ 有条件可行 | 仅对 1 个源(首页源)做 ≈ 7.5~72 MB,见 6.3 |
| 缓存**用户搜过的关键词**的结果 | ✅ | 成本近零、无假阴性(结果就是源站给的)、收益直接 |
| 缓存**负结果**(源×关键词=空) | ✅ | 成本极低,重复搜索收益巨大 |
| 缓存**热搜榜/建议词**的搜索结果(预热) | ✅ | 命中率高,可后台低优先级做 |

## 3. 存储影响

### 3.1 单条记录大小(依据:实际字段集)

索引一条影片需要保留的字段,以 `AbsJson.AbsJsonVod.toXmlVideo()` 实际映射的字段为准(UTF-8 字节):

| 档位 | 包含字段 | 估算大小 |
|---|---|---|
| **瘦**(仅检索必需) | `name` + `alias` + `id` + `sourceKey` + `type` + `year` + `area` + `lang` + `note` | **≈ 250 B** |
| **标准**(可展示卡片) | 瘦 + `pic`(URL)+ `actor` + `director` + `score` | **≈ 600 B** |
| **全量**(含简介) | 标准 + `des`(源站 `vod_content` 正文,实测样例 ≈ 450 汉字) | **≈ 2.4 KB** |

推导依据(取仓库内真实样例字段):
- `name` 如「咸鱼先生，Rose小姐之彗星来了」≈ 15 字 ≈ 45 B
- `alias`(`vod_sub` + `vod_en` 合并)≈ 100~150 B
- `pic` URL ≈ 70 B;`actor` ≈ 60 B;`director` ≈ 40 B
- `des` 正文样例约 450 汉字 ≈ **1 350 B**(这一项单独就把记录从 600 B 抬到 2 KB)

若按 JSON 存储还要加键名开销(约 15 个键 × 8 B + 引号 ≈ +150 B),故 JSON 形态为 400 B / 750 B / 2.6 KB。

### 3.2 内容量(依据:仓库内真实响应样例)

`AbsJson.java` 里保留的真实响应样例:

```
"page": 2,  "pagecount": 209,  "total": 4166      // 单个分类(t=32 国产剧),每页 20 条
```

即:**一个中等规模站点的"单个分类"就有 4 166 部**,页数 209。

一个聚合站通常 20~40 个分类,但分类之间**大量重叠**(一部片会同时出现在「电影」「动作片」「2023」里),去重后**独立条目数**保守取 **3 万**作为中位估计(小站 3 千~1 万,大站 10 万+)。

### 3.3 乘法表

单源占用 = 3 万条 × 记录宽度:

| 档位 | 单源 | 30 个源 | 328 个源(本机实测数) |
|---|---|---|---|
| 瘦 250 B | 7.5 MB | 225 MB | **2.46 GB** |
| 标准 600 B | 18 MB | 540 MB | **5.9 GB** |
| 全量 2.4 KB | 72 MB | 2.16 GB | **23.6 GB** |
| 瘦 + bigram 索引(×2.5) | 19 MB | 563 MB | **6.15 GB** |
| 全量 + bigram 索引(×2.5) | 180 MB | 5.4 GB | **59 GB** |

### 3.4 结论:会暴涨,且是"线性爆炸"

**会不会随数据量增长而暴涨?会。** 而且它同时随三个乘数线性增长,没有任何自限机制:

```
占用 = 源数 × 每源片数 × 记录宽度 × (1 + 索引膨胀系数)
```

- 源数:用户加订阅就会涨(本机已 328,聚合订阅动辄数百)。
- 每源片数:源站每天更新,长期单调增长(只增不减)。
- 记录宽度:一旦想展示简介/演员,就从 250 B 跳到 2.4 KB(**10 倍**)。
- 索引膨胀:中文子串检索需要 2~3 倍。

**没有任何一档能落在可接受区间**:最省的"328 源 + 瘦记录"也有 2.46 GB,而本机**应用数据总量现在是 59 MB** —— 相当于把 App 数据扩大 **42 倍**。在电视盒子上这是致命的(盒子常配 8~16 GB 存储)。

要让占用"不随数据量增长",唯一办法是**让缓存量的上界由"用户行为"决定,而不是由"源的内容量"决定** —— 即按需缓存 + 硬上限。见 6.2。

## 4. 缓存失效策略

### 4.1 三种清理时机的评估

| 时机 | 评价 | 理由 |
|---|---|---|
| **占用达阈值时清理** | ✅ **应作为主机制** | 唯一有界的手段;与数据量解耦;可按 LRU 精确淘汰 |
| **按 TTL 过期** | ✅ **应作为主机制** | 解决"内容变了"的问题(一致性,见第 5 节);TTL 与容量是两个不同维度,缺一不可 |
| **正常退出/软关闭前移除** | ❌ **不能作为主机制** | 见 4.2 |
| 启动时孤儿清理 | ✅ 作为兜底 | 项目已有先例 `SubtitleCacheJanitor` |

### 4.2 为什么"退出时移除"不能作为主机制

四条理由,前两条是硬事实:

1. **Android 不保证进程退出回调**。"正常退出"在 Android 上不存在可靠定义 —— 用户按 Home、切后台、系统回收、崩溃、断电、直接强停,都不会调用 `Application.onTerminate()`(`onTerminate` 只在模拟器上会被调用)。靠它做清理 = 绝大多数情况下不执行。
2. **"清除"会把收益清零**。这个需求的全部价值在"下次搜索更快";若每次退出都清,则下次冷启动冷缓存,**收益归零**,只剩存储省下来 —— 那不如干脆不做缓存。
3. **进程被杀时写 KV 也不可靠**。`avbox-kv-mmkv-spec.md` §4.1 已有实测结论:MMKV 写入是**异步**排进 Scheduler(约 1 秒后落盘),2.4.2 没有同步写 flag;崩在 1 秒内该写根本没落盘。所以"退出前写一次清理标记"这类设计在本项目上已被证伪过一次。
4. **冷启动扫描大目录会拖慢启动**。若把"清理"放在启动路径(为绕开退出不可靠),又会与"提升搜索速度"的初衷冲突:启动时扫几十 MB 的表并删除,是数百 ms 到秒级的 IO。

**若确实想要"退出即清"**:只能作为**用户可选的显式开关**(如"退出时清除搜索缓存"),且必须在设置页写清代价(下次搜索变慢);不能是默认行为,也不能是唯一机制。

### 4.3 推荐的分层失效

```
L1 内存缓存(进程级)
  · 关键词 → 结果列表;仅会话内有效,进程死即消失
  · 上限 200 个关键词(小对象,几 MB 内存)
  · 作用:同一次会话里改词再改回来、返回再进搜索页 —— 零延迟

L2 落盘缓存(Room,按需写入)
  · 上限:条数 5 000 条 OR 体积 20 MB(取先到者)
  · TTL:正结果 24 h;负结果 6 h(负结果更易过期,见 §5)
  · 淘汰:LRU(按 lastHitAt)
  · 触发清理的三个点:
      ① 写入时:用量 > 上限 80% ⇒ 按 LRU 淘汰至 70%(水位线,避免每次写都淘汰)
      ② 启动时:janitor 清 ①过期条目 ②孤儿条目(源配置已不存在的)
      ③ 设置页:用户手动「清除搜索缓存」+ 显示当前占用

L3(可选)预热
  · 用热搜榜/建议词在**充电 + 息屏 + 有 WiFi**时低优先级预热
  · 严格限流:每次会话 ≤ 20 个词,且复用正常搜索链路(不另开爬取通道)
```

**水位线(80% → 70%)的理由**:若"到 100% 才淘汰一条",则每次写入都触发一次淘汰 + 一次磁盘整理,写放大严重;留 10% 余量让淘汰是批量、低频的。

**为什么把 L2 放 Room 而不是 MMKV**:MMKV 是 **mmap 整个文件**,写入是"改内存页 + 异步刷盘",适用小对象(本机 `avbox_kv` 才 64 KB)。放 MB 级缓存会出现:①每次 `commit` 都可能重写/增长映射文件;②`allKeys()` 遍历变慢(规范已警告"不要在热路径调用");③动态键族无法逐键登记 `KVKeySpec`,有"登记类型与写入类型不一致 ⇒ 静默读不出"的风险 —— `avbox-kv-mmkv-spec.md` R10/R11 已记录过该风险面。Room 有真索引、可按条件删除、可按 `LIMIT` 淘汰,这才是它的用途。

## 5. 数据一致性

### 5.1 冲突的本质

缓存的是"**某源在某时刻对某关键词的回答**",而源站的内容、乃至源本身都在变:

| 变化 | 影响 |
|---|---|
| 源站补资源(今天没有,明天有) | 负缓存变成**假阴性** ⇒ 用户搜不到 |
| 源站删/改名 | 正缓存指向已失效条目 ⇒ 点进去是空详情 |
| 用户换仓(切 `api_url`) | 整个源集合换掉 ⇒ 缓存**全部**失去意义 |
| 用户改搜索站点勾选 | 缓存遮蔽了用户"这次想搜更多源"的意图 |
| 源被自动屏蔽(2026-10-08 新机制) | 缓存里仍有死源的结果 ⇒ 换源/播放阶段白等 |

### 5.2 推荐的一致性机制

**① 条目必须带三个版本戳,任一不匹配即作废(不是"刷新",是"作废"):**

```
cacheEntry(
  keyword,                 // 归一化后的关键词(与 SearchSettings.normalize 同口径)
  apiUrl,                  // 当前源集合地址(HawkConfig.API_URL)
  sourceKey,               // 具体源
  configFingerprint,       // 源配置指纹(订阅内容 hash)
  fetchedAt, lastHitAt, ttlMs,
  isNegative,              // 负结果标记
  payload                  // 结果列表(瘦档字段)
)
```

作废判据与项目既有口径对齐:
- `apiUrl` 比对 —— 先例 `SearchViewModel.checkedSourcesApiUrl` 的过期判定(`SearchViewModel:225`)。
- `configFingerprint` —— 先例 `SearchHelper.isSelectionStale()` 的思路:源集合变了,选择就过期。
- 源被屏蔽 —— 直接调 `SourceHealthMemory.blockedKeys()`,把命中缓存里该源的条目**跳过**(不删,解封后还能用)。

**② 正结果用 stale-while-revalidate(先给旧的,后台刷新的):**

```
命中缓存 → 立刻渲染(零延迟,这是收益的来源)
         → 同时后台发起正常搜索(复用 SearchViewModel 原链路)
         → 回来后覆盖缓存 + 推送增量
```

这样"快"和"准"都拿到:用户第一屏瞬间出结果,几百毫秒到几秒后结果被实时数据补齐/纠正。**关键是 UI 不能把缓存结果当成"最终结果"** —— 需要有一个"正在核实"的轻提示,否则用户会以为搜完了。

**③ 负缓存的 TTL 必须显著短于正缓存(6 h vs 24 h),且只对"源明确回答空"生效:**

| 源返回 | 能否进负缓存 | 理由 |
|---|---|---|
| `Empty`(HTTP 200,结果为空) | ✅ 可以 | 源明确说"我没有" |
| `Timeout`(8s 未回) | ❌ **不可以** | 这是"源可能死了",属**源健康**问题,归 `SourceHealthMemory` 管;当负缓存会把"临时慢"误记成"永远没有" |
| `Failed`(HTTP 错误) | ❌ 不可以 | 同上 |

⚠️ **与既有 `AvailabilityMemory` 的口径必须分开**:后者是**内容级**标记("这部片在**所有**源都没资源",TTL 90 天);搜索负缓存是**源级**("这部片在**这个**源没有",TTL 6 h)。两者语义不同、TTL 差 360 倍,绝不能共用一个 TTL —— 那正是"换个源从头播"式 bug 的温床。

**④ 换仓/改源时不做迁移,直接整体作废。** 应用未发布、无存量包袱(项目既有决策),旧条目让它被 janitor 自然清掉即可,不值得写迁移代码(参考 `avbox-kv-mmkv-spec.md` Q5 的决策逻辑)。

## 6. 方案建议

### 6.1 方案 A:全量目录本地索引 ❌ 不推荐

- 结构:`Room titles(sourceKey, normalizedName, alias, id, …)` + `Room bigram(token, titleId)`。
- 优点:搜索瞬时、离线可搜、不依赖源站存活。
- 缺点:**第 2 节的全部风险** —— 协议层拿不到全量、百万级请求/数十 GB 流量/数小时、假阴性、封 IP、GB 级存储、索引语义复刻不全、type 3 源不可离线枚举。
- 判断:**技术上不可实现,产品上得不偿失**。若仍要做,唯一能自洽的形态是"**只索引 1 个首页源**"(见 6.3)。

### 6.2 方案 B:按需关键词结果缓存 + 负结果缓存 ✅ **推荐(P0)**

- 结构:一张 Room 表(字段见 §5.2),不建倒排索引(检索键就是"归一化关键词"本身,单列索引足够)。
- 写入时机:正常搜索链路返回后写(零额外请求)。负结果只在"源明确空"时写。
- 读取时机:输入关键词后**先查表** → 命中则立即渲染 + 后台核实。
- 优点:
  - **零额外网络成本**,不增加任何对源站的请求;
  - **无假阴性**:缓存内容就是源站当时的回答,不存在"索引没覆盖到";
  - 存储有硬上限(5000 条 / 20 MB),**不随源数增长**;
  - 实现量小(1 张表 + 1 个缓存层 + 1 个 janitor),不触碰抓取侧。
- 缺点:
  - 只对**重复搜索**生效;长尾关键词命中率低;
  - 解决不了"首次搜某词仍然 2.4 分钟"的问题。

### 6.3 方案 C:首页源单源索引 ⚠️ 可选(P1)

- 只对**当前首页源**做目录枚举(分类 × 页码),其余源不碰。
- 优点:覆盖用户最可能搜的源;离线可搜;占用可控(**7.5 MB 瘦档**,即使含简介 72 MB 也可接受)。
- 缺点:仍是"单一源"覆盖,其他源上有的片依然搜不到;需要后台任务 + 断点续传(翻页中断很常见);与"本地索引只能召回不能判定"的限制共存。
- **必须配一条产品约束**:本地索引命中**不阻断**在线搜索。UI 上应是"本地结果(先显示)+ 在线结果(随后补齐)",绝不能因为本地有结果就不发在线请求 —— 否则就是 §2.4 R1 的假阴性事故。

### 6.4 对比

| 维度 | A 全量索引 | B 按需缓存(推荐) | C 单源索引 |
|---|---|---|---|
| 协议可行性 | ❌ 不支持 | ✅ 不需协议支持 | ⚠️ 部分支持 |
| 额外网络成本 | 308 万请求 / 92~924 GB | **0** | 约 9 400 请求 / 0.3~2.8 GB |
| 首次搜索提速 | 瞬时 | 无提升 | 该源瞬时,其余无提升 |
| 重复搜索提速 | 瞬时 | **瞬时(命中时)** | 该源瞬时 |
| 存储(本机规模) | 2.46 GB ~ 59 GB | **≤ 20 MB(硬上限)** | 7.5~72 MB |
| 假阴性风险 | **高** | **无** | 中(需"不阻断在线") |
| 封 IP / 风控风险 | **高** | 无 | 中 |
| 实现量 | 极大 | **小** | 中 |
| 数据新鲜度 | 差(日更,索引滞后) | 好(24 h TTL + 后台核实) | 中 |

### 6.5 收益排序(哪些改动更值)

按"实测痛点 → 最省力的对症手段"排:

| 优先级 | 手段 | 预期效果 | 依据 |
|---|---|---|---|
| **1** | **源屏蔽机制(已实现,2026-10-08)** | 289 个超时源被逐步剔除 ⇒ 一轮搜索从 328 源降到几十源 | 实测 timeout 289/328 |
| **2** | **按需结果缓存 + 负缓存(方案 B)** | 重复搜索瞬时;负缓存直接跳过已知无结果的源 | 零额外成本 |
| 3 | 已有命中即提前收敛(找到可信命中就停后续批次) | 首屏更快 | `SearchBatchPolicy.shouldAutoContinue` 已有雏形 |
| 4 | 热搜词预热(方案 B 的 L3) | 头部关键词命中率提升 | 已有 `HOME_HOT` 当日缓存 |
| 5 | 方案 C 单源索引 | 只在"首页源搜索"场景有效 | 成本/收益一般 |

**结论:先做 1+2 即可拿到绝大部分体感提升(且几乎零成本);3 是小改动高收益;4/5 按需再说;方案 A 不做。**
